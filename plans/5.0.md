# Plan: jsonrpcclient 5.0

Tracking issue: [#252](https://github.com/bensynapse/jsonrpcclient/issues/252). Started 2026-11-06, from 4.1.0
(`403603e`). The server went through the same steps the same day, in
[jsonrpcserver's 6.0 plan](https://github.com/bensynapse/jsonrpcserver/blob/main/plans/6.0.md).

## Branches

- `main` is 5.0 development from now on. `__version__` is `5.0.0.dev0` until the first release candidate.
- `release/4.x` (from the 4.1.0 tag) carries 4.x fixes. It has the same protection as main ("CI OK" required,
  admins included, no force push). `release.yml` already accepts tags on `release/` branches.
- Every change reaches main through a pull request with green "CI OK", one increment at a time.

## What 5.0 is for

4.x works, but a few things in it can't be fixed without breaking someone:

1. **Batches are a one-pass iterator.** `parse` on a list gives a lazy `map`. Reading it twice gives nothing the
   second time, and a malformed item raises halfway through a loop, after the items before it were used.
2. **Batch responses have to be matched by hand.** Every user writes the same dict comprehension. The docs list three
   edge cases where it silently loses an error.
3. **`InvalidResponse` subclasses `KeyError` and `TypeError`.** That kept 4.0 `except` clauses working in 4.1, but
   it means `except KeyError` around unrelated code catches a bad response, and the reverse.
4. **Nothing checks what goes into a request.** `request("sqrt", "16")` sends `"params": "16"`, which no server
   accepts, and the mistake only shows up as an error from the server.
5. **Old Pythons.** 3.8, 3.9 and 3.10 have reached end of life. They hold the code to `Optional`, `Dict` and `List`.

## Decisions

| | Decision | Why |
|---|---|---|
| D1 | `requires-python >=3.11`. CI tests 3.11 to 3.14 and 3.14t. The code uses `X \| Y`, `list[...]` and `dict[...]`. | The same floor as jsonrpcserver 6.0. 3.10 reached end of life in October 2026. 3.11 also brings `typing.NotRequired`, which D7 needs, without typing_extensions. On an older Python pip keeps installing 4.x. |
| D2 | `parse` on a list returns a `list` of `Ok` and `Error`. It checks every item before it returns, and a bad item raises `InvalidResponse` naming its index. `parse_json` does the same for a JSON array. | A list can be read twice, indexed and measured. Checking up front means a loop never sees half a batch. Code that loops, calls `list()` or builds a dict keeps working. Only `next(parse(batch))` breaks. |
| D3 | A new function, `match_responses(requests, responses)`, returns a dict from each request id to its response, in the order of the requests. Notifications are skipped. | It handles the edge cases from the Batches page in one place, instead of in every caller. Rules below. |
| D4 | `InvalidResponse` subclasses `ValueError`, not `KeyError` and `TypeError`. It's the one exception for a reply that isn't valid JSON-RPC, from `parse`, `parse_json` and `match_responses`. | `json.JSONDecodeError` is a `ValueError` too, so one `except ValueError` catches "not JSON" and "not JSON-RPC". The old base classes were only for 4.0 code, which 4.1 already moved off. |
| D5 | `request`, `notification` and the `_json`, `_hex`, `_random` and `_uuid` variants raise `TypeError` when `method` isn't a `str`, or `params` isn't a list, tuple or dict (or None). | The type hints already say so. A wrong type is a bug in the caller, and failing at the call shows where it is. A method name starting with `rpc.` stays allowed, since a client may call the server's own `rpc.discover`. |
| D6 | `parse(..., strict=True)` and `parse_json(..., strict=True)` also check that `"jsonrpc"` is `"2.0"`, that a response has exactly one of `result` and `error` (a null `error` counts as present), that `error.code` is an int and `error.message` a str, and that `id` is a string, a number or null. The default stays lenient, as in 4.x. | The spec says MUST for each of these. They're opt-in because real servers break them, and 4.1 made `parse` accept JSON-RPC 1.0 style errors on purpose. Bools aren't numbers here, though Python says they're ints. |
| D7 | `request` returns a `Request` and `notification` returns a `Notification`, both `TypedDict`s, exported from `jsonrpcclient`. `params` is `NotRequired`. `id` stays `Any`, as the `id` argument is. | A type checker sees the fields. It's a static change only: at run time they're still plain dicts. |
| D8 | `parse_json`'s `strict` keyword now means D6. 4.x passed it on to `json.loads`, where it allows control characters in strings. | The obvious name for D6, and the clash is rarely hit. Code that needs `json.loads(strict=False)` can call `parse(json.loads(text, strict=False))`. Neither meaning fails silently: a control character gives `JSONDecodeError`, and a non-2.0 reply gives `InvalidResponse`. |
| D9 | `Ok`, `Error`, `Response`, the id generators, `compose`, `request_natural` and the `_json` variants keep their names and signatures. | They work, and renaming them would only break code. |
| D10 | Release 4.2.0 from `release/4.x` first. It gives a `FutureWarning` for a `method` that isn't a str, `params` that aren't a list, tuple or dict (D5), and `parse_json(..., strict=...)` (D8). On Python 3.8 to 3.10 importing jsonrpcclient warns once that 5.0 needs 3.11. | Each of these is cheap to detect and changes behaviour in 5.0. A batch read as an iterator, and an `InvalidResponse` caught as `KeyError` or `TypeError`, can't be detected at run time, so they get no warning. The changelog points at this plan. |

### match_responses (D3)

`match_responses(requests, responses)` takes the batch as sent and what `parse` returned for the reply.

- Each request with an `id` maps to the response with the same id. Requests without one are notifications and
  are skipped. Two requests with the same id raise `ValueError`, as they can't be told apart.
- If `responses` is one `Error`, the server rejected the whole batch, and every request maps to that error.
  One `Ok` raises `InvalidResponse`.
- A response with `"id": null` that matches no request is an error the server couldn't tie to a request. A request
  with no response of its own gets one of those, in order. With none left, it raises `InvalidResponse`, as does a
  response whose id matches no request, and two responses with the same id.
- Ids must be hashable, as JSON-RPC ids (strings, numbers, null) are.

## Increments

Each is one pull request into main. Each keeps every repo gate green. The gates are tests at 100% coverage, ruff
check and format, and mypy and pyright in strict mode. Then the package build checks, the README and docs examples
with every transport installed, and `mkdocs build --strict`. Tests come first where behaviour changes.

1. **This plan.**
2. **Python 3.11** (D1). `requires-python`, the classifiers and badge, the CI matrix, tox, ruff's `target-version`,
   mypy's and pyright's Python version. `ruff --fix` applies the UP rules. The version becomes `5.0.0.dev0`.
   `release.yml` marks a version with a letter in it as a pre-release on GitHub, as the server's does.
3. **Batches as lists** (D2).
4. **`InvalidResponse` is a `ValueError`** (D4).
5. **Runtime checks on requests** (D5).
6. **`TypedDict` requests** (D7).
7. **Strict mode** (D6, D8).
8. **`match_responses`** (D3).
9. **Docs.** The migration guide from 4.x to 5.0, the changelog, the README, and issue 252's checklist.
10. **Release.** 4.2.0 from `release/4.x` (D10) comes before increment 2. `5.0.0rc1` comes from main after 9.

Out of scope for 5.0: transports (jsonrpcclient builds and parses, and stays that way), async helpers, and
response `TypedDict`s.

## Acceptance

- Code that builds requests with `request` or `notification`, sends them, and reads one response with `parse`
  runs unchanged on 5.0 (a test pins this).
- Every changed or removed behaviour is in the migration guide, with the replacement.
- The package still has no runtime dependencies.
- All repo gates are green on main, and `release/4.x` can still release.
- `pip install jsonrpcclient` keeps installing 4.x until 5.0.0. `pip install --pre jsonrpcclient` installs the
  release candidate.

## Risks

- **Code that uses a batch as an iterator.** `next(parse(batch))` raises `TypeError` on 5.0. Nothing can warn about
  it in 4.2.0. The migration guide shows `parse(batch)[0]` and `iter(parse(batch))`.
- **`except KeyError` or `except TypeError` around `parse`.** It stops catching `InvalidResponse`. Nothing can warn
  about it either. The migration guide says to search for it.
- **Typed callers that annotate requests as `dict[str, Any]`.** mypy doesn't accept a `TypedDict` there. The
  migration guide shows `Request` and `Mapping[str, Any]`.
- **A server that sends ids `match_responses` can't match.** It raises `InvalidResponse` with the id in the
  message, and `parse` on its own still works.
